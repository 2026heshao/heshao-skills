# 无本地编译时的 CI 验证防线

## 何时用

- 本机**没有工具链**（无 JDK / SDK / Gradle / aapt2），改动只能靠远端 CI 才知道能不能编译。
- 本地有脚本检查器（`check_*.py` 之类正则静态检查），需要判断**它能覆盖什么、绝对覆盖不了什么**。
- **CI 红了**，要先归因再修（尤其是同一类错误反复出现时，多半是本地防线有洞，而不是写代码的人粗心）。
- 准备**推一批从未编译过的代码**（大重构、多文件迁移、多人并行改动叠加）。

> 本文中的 Android/Kotlin 实证取自 Healix 项目 CI run #26–#53（六个失败批次），
> 但每条都给出**语言无关的判别方式**，非 Kotlin 项目可直接套用。

---

## 第 0 步：先画清本地防线的边界

把 CI 的每个步骤列出来，逐个问「本机能不能提前做」：

| CI 步骤类型 | 本机可覆盖 | 典型代表 |
|---|---|---|
| 自定义静态检查脚本 | ✅ 同源，推送前必须本地全绿 | `check_resources.py` / `check_kotlin.py` / `check_schema.py` / lint 脚本 |
| **资源 / 清单编译** | ❌ 本机没有编译器 | Android `processDebugResources`（aapt2）：XML 注释含 `--`、资源引用、Manifest 规则 |
| **源码编译** | ❌ 只有 CI 能证 | `compileDebugKotlin`：符号解析、可见性、suspend/async 上下文、泛型推断 |
| **单元测试** | 🟡 可在 CI 真跑，但需先抽纯函数 | `testDebugUnitTest` |
| **编译期生成产物校验** | ⚠️ 产物只能来自 CI | Room schema JSON（KSP 编译期生成，本机无 JDK 造不出来）→ 用脚本从 CI artifact 拉回 |
| 真机行为（崩溃 / UI） | ❌ | 需要崩溃捕获器 + 用户实机反馈 |

**判据**：凡「需要符号解析 / 类型系统 / 编译器插件」的环节，本机零覆盖。
本地检查器再全绿也只说明**没犯已覆盖的错**。

## 1. 静态检查器的原理性盲区清单（本地全绿照样 CI 红）

正则型检查器**不做符号解析、不做类型推断、不解析 XML**，以下每类都有真实 CI 失败实证：

| # | 盲区类型 | 典型报错形态 | 为什么检查器抓不到 |
|---|---|---|---|
| 1 | **调用不存在的方法** | `Unresolved reference: xxx` | 需要跨文件符号表 |
| 2 | **public 成员暴露 internal/包私有类型** | Kotlin: `public function exposes its ... parameter type` | 需要类型 + 可见性推导 |
| 3 | **import 路径 / 包名写错** | `Unresolved reference`（库在子包里） | 需要类路径解析 |
| 4 | **漏 import（文件迁移漏抄）** | 一片 `Unresolved reference: launch` 等 | 需要「用到了但没导入」的符号追踪 |
| 5 | **限定引用写错作用域** | companion 内的**嵌套类**不能写 `Outer.Nested`；**顶层 const** 不能写 `ClassName.X` | 需要作用域模型 |
| 6 | **表达式体转发挂起函数** | `fun x() = suspendCall()` → `should be called only from a coroutine` | 多数检查器只扫**块体** `{ ... }` |
| 7 | **非 suspend 函数体直调挂起方法** | 普通 `build()` 里调 `dao.get()` / `dao.listInRange()` | 同上，且调用常带接收者 |
| 8 | **空嵌套容器泛型推断失败** | `mapOf("type" to "object", "properties" to mapOf())` 推不出 K/V | 需要类型推断 |
| 9 | **产端与解析端字面不一致** | 生产 `"本次问了 N 项"`，消费端按 `startsWith("查阅：")` 认 | 检查器不理解跨文件的字符串契约 |
| 10 | **资源文件注释合法性问题** | Android XML 注释里写 `--`（如原型出处 `var(--text_1)`）→ aapt2 直接拒 | 本机不跑资源编译器 |

### 1.1 作用域 / 限定引用速查（最易混，通用规则）

| 声明位置 | 写法 | 合法性 |
|---|---|---|
| 类伴生对象内的**常量** | `Outer.X` | ✅ 合法 |
| 类伴生对象内的**嵌套类型** | `Outer.Nested` | ❌ 编译器不认这种限定 |
| **顶层（包级）常量** | `ClassName.X` | ❌ 顶层常量不是类成员 |
| 以上任何一种 | `import` 后裸用 | ✅ **唯一保险写法** |

**陷阱**：顶层常量在**同一个包内**可以写 `ClassName.X` 看着很像能用（其实编译器看的是包符号，不是类成员），
跨文件 / 跨包才炸 → `import` 后裸用是唯一稳定形态。

## 2. 判别「静默失效」——比盲区更危险

盲区是「检查器没这个功能」，**静默失效是「检查器在跑、步骤全绿，但对报错的那段代码零覆盖」**。

### 2.1 真实病例（务必读懂机理）

某检查器 `check_suspend_calls` 存在多年，CI 报错的同一段代码**它一个字都没报**：

| 根因 | 机理 |
|---|---|
| 正则负向后顾 `(?<![\w.])NAME\s*\(` **排除了 `.` 前缀** | 而 DAO/Repository 调用的典型形态恰是**带接收者**的 `eventDao().listInRange(...)` → **全部漏报** |
| 「函数体内已有协程作用域则短路」只认标准库写法 `runBlocking` | 项目自有的 `runBlockingSafe` 因后跟字母（无词边界）匹配不到 `\brunBlocking\b` → 假阳/漏判同时存在 |

修法（可迁移到任何语言的检查器）：

1. 判定者接受**两种形态**：裸调用 `name(` ∪ **接收者指向挂起源**（`Dao/Repository/db/database`）的 `receiver.name(`。
2. ★ **必须按接收者收敛**：不收敛会把标准库同名方法（`list.find{}` / `map.remove(k)` / `LocalDate.parse(s)`）
   当成危险调用 —— **实测放宽后一次误报 15 条，真信号被噪声淹掉**。
3. 短路白名单补上项目自有的包装函数。

### 2.2 坏例自证铁律（不可跳过）

**改任何检查器 / 新增任何检查器，必须按此 SOP：**

```
1. 构造与真实 bug 同形态的坏例（不是随手改个字符串）
2. 注入 → 必须精确报出
3. 还原 → 全项目复跑必须 0 误报
4. 把「修正前该坏例零报出」这句话写进记录
```

★ **不先验证「坏例能不能报出」，等于给检查器发一张永远绿的假通行证。**
历史上已出现两次「以为有防线、实际零覆盖」：`check_view_binding`（曾整体静默跳过）、`check_suspend_calls`（上例）。

## 3. 推 CI 前的手工核对清单（本机无编译器的唯一替代）

每次推送前逐项跑，**脚本能跑的就用脚本跑**：

1. **跨文件符号双向核对**：新增代码里每个跨文件引用，`grep` 调用点 ↔ 定义两端都存在。
   实体/结构体**构造参数名逐个比对**（非空字段 vs 可空字段对应不同读法；不传的字段必须有默认值）。
2. **可见性**：公开签名（函数参数、返回类型、公开 Flow/Channel 的泛型实参）里出现的类型必须足够公开。
3. **import 迁移核对**：任何「把文件 X 的内容迁到 Y」的操作，逐个对照原文件的 **import 段**（头号遗漏点）。
4. **视图绑定 / 资源 ID**：`binding.field` ↔ 布局 `@+id` 逐一核对。
5. **格式化占位符**：`%1$s/%2$s/%3$d` 之类 ↔ 调用点实参**个数**核对。
6. **常量唯一性**：同值同名常量在多个伴生对象里会撞检查规则 → 就地改名。
7. **挂起/异步上下文**：函数体只要出现 `xxxDao().NAME(` / `xxxRepository.NAME(` / 裸异步调用 →
   该函数**必须**标 `suspend`（或等价 `async`），或其调用点被 `launch {}` / `withContext {}` / 项目自有包装器包裹。

> 已知仍覆盖不到的：`get` 这类「全工程存在同名非挂起定义」的名字会被合理排除 → 这类只能人工看。

## 4. 归因纪律（保住「CI 红了能知道是谁」）

- **未验证批次单独推、单独跑 CI；绿了再叠下一批修复**。多个批次叠加推送 = 红了无法归因。
- **多会话 / 多智能体共用工作区**：
  - 对方的未提交改动，只要你 `git add` 到同一文件就会被你的提交夹带 → 先看 `git status` + mtime 再动手。
  - 若必须代提交，**单独成 commit 推上去验绿**，再在绿基线上叠自己的。
  - 发布脚本应走**对象库**（`git cat-file` / `ls-tree`）而非工作区 → 天然不夹带未提交改动（推之前 `--dry-run` 确认范围）。
- 提交契约：代提交前先验项目硬性约束（如协议版本号、冻结文件是否被改动）。

## 5. CI 红了之后的标准动作

```
1. 取失败日志上下文（不是只看结论），把错误逐条归类 → 对照 §1 盲区表
2. 判断这是「新盲区」还是「检查器失效」：
   - 检查器没有这个功能 → 盲区
   - 检查器有这个功能却一条没报 → 静默失效（优先级更高）
3. 最小修复单独成 commit + 单独推 + 单独跑 CI（保归因）
4. 补防线：加检查器 or 修检查器 → 必须走 §2.2 坏例自证 → 再来一轮 CI 验证零误报
5. 把这次的根因写进检查器的注释/文档（防重犯）
```

**轮询细节**：run 状态从 `in_progress` 到 `completed` 只隔几秒是正常的（run 早就跑了几分钟，刚好赶尾巴）
→ **用独立第二次查询复核 run 编号 + job 结论再下结论**，别凭单次快照报喜报忧。

## 6. 无法在本机验证的逻辑 → 搬到 CI 上真跑

编译器只能告诉你能不能编译，**逻辑正确性要另外的手段**：

| 手段 | 适用 | 要点 |
|---|---|---|
| **抽纯函数 + 真单测**（首选） | 有实际单测 Runner | 把计算从渲染/IO 里剖出来：`factOf(...)` 无 Context 无 IO 可断言，`render(ctx, ...)` 只贴文案。分开才有 CI 证据 |
| **可执行状态机模型** | 无单测 Runner / 逻辑与平台 API 缠死 | 用脚本语言忠实复刻状态机（如跨零点日期判定），**枚举场景**（如 8 个跨零点场景 8/8 PASS） |
| **规范化 diff 复核** | 重构「抽方法」类改动 | 抽出来的代码 vs 原内联块，`difflib` 规范化后比对，应零差异；**不采信执行者自述** |

★ **单测必须固定时间戳、不读系统时钟** —— 否则会在跨零点偶发变红。

## 7. 发布与产物链条的实用细节

- **远端对象写入的偶发失败**（如 Git Data API 的 tree POST 返回 422）已成确定性现象（相同操作复现约 10 次）：
  每次都是「重跑一轮即全中」→ **直接重跑补齐，不要手写补传脚本**（手写会漏掉幂等语义）。
- **凭据纪律**：读取凭据脚本若只取文件「第一行」→ 先切出只含凭据行的临时文件再传，**用完即删**；勿直接传含其它内容的文档。
- **仓库完整性**：清理由脚本建错的临时 git 对象时，**单个文件删除即可，绝不跑 `git prune`** —— 可能挂着别人丢失的提交。
- **大产物下载**：30MB+ 的 artifact 在前台会被 SIGTERM 杀掉 → **必须放到后台跑**（后台实测 7 分钟跑完 33MB）。
- **CI 步骤顺序**：依赖编译产物的校验步骤（如 schema 完整性检查）必须排在编译步骤**之后**。
- **真机兜底**：自签证书每轮不同 → 覆盖安装前先卸载旧版；加崩溃捕获器把堆栈落盘并允许分享，
  **没有 logcat 也能拿到真机真实堆栈**。

## 附：一句话判据

> **本地检查器全绿，只代表「没犯已覆盖的错」；犯的是「没覆盖的错」时它照样全绿。**
> 每次 CI 红了，第一件事不是改代码，而是问：**这类错误本地防线为什么没拦住？能不能补一条带坏例自证的检查器？**
