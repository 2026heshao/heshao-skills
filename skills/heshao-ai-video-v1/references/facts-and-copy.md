# 事实与文案 / Facts & Copy

## 1. 事实表先于文案

每一句上屏内容都要有出处：

| 上屏内容 | 真实出处 | 是否上屏（是/否/仅脚注） | 说明 |
|---|---|---|---|
| 版本号 | `package.json` | 不要沿用旧 README 横幅 |
| 面板分类 | 代码常量 / 渲染函数 | 字面英文还是 i18n |
| 按钮文案 | 词条表 + 渲染行 | 忙碌态、空态、错误态 |
| 命令 | README 安装段 | 桌面端/网页端 profile 不同 |
| 数字 | 代码/接口/文档 | 实时数 vs 硬编码占位符 |
| 状态 | 代码分支 | 已安装/需授权/未连接 |
| 演示数据 | 自己编的 | 否（或仅脚注） | 必须角标“演示/示例” |
| 本机数量 / 路径 / 账号名 | 本机 `scan`·`status`·`verify` 实跑 | **开工前与用户确认** | 默认「否」。删不掉的那部分（界面帧里 App 自己算出来的数字）三选一：演示数据集重拍 / 放大裁切出画 / 保留 + 脚注「数量随机器而变」 |

### 规则

- 没有出处就不上屏；不能为了画面“看起来丰富”编功能。
- 旧片的数字不能直接搬进新片；先核对当前版本。
- 演示数据要标明；不要写“实时”除非真的是实时接口。
- 静态数字与动态数字分开：`19 万+` 是占位符原文，不是实时库存。
- 卡片/面板是“示意重绘”时，在画面角标写“示意界面”。
- **本机数据的口径在事实表阶段就要问死**：技能数量、格位数、体积、账号名、本机路径这类"真实但不该上屏"的数字，
  默认按「旁白 / 字幕 / 我写的标注里不出现」准备；界面帧里 App 自己算出来画上去的数字删不掉，
  要么用演示数据集重拍并标「演示数据」，要么放大裁切把它移出画面，要么保留并脚注「数量随机器而变」——
  三选一，开工前让用户定，别等看完预览才发现（2026-11-05 skilllocker 实测：v1 里 56 / 392 / 16 / 48 / 27.6 MB
  全部上屏，用户看完预览才要求撤掉，文案与字幕返工一轮，还多花一次 TTS 重跑）。

## 2. 本片踩过的两个事实坑

1. **Skill 卡没有“上次调用”**：Skill 看板只有装于、来源/市场原名、分类、启用状态；上次调用属于工具裁缝。把“上次调用”塞进 Skill 卡，画面好看但事实不对。
2. **三类资产不能共用“最近安装”排序**：`最近安装` 是 Skill 看板的视图；MCP/专家卡不应跟着它重排。翻账幕因此收窄为三张 Skill 卡。

教训：**先决定这一幕到底在哪个真实界面，再决定字段。** 不要把多个界面的字段拼成一张“更好看”的卡。

## 3. 文案骨架

```text
钩子：一句提问/损失/反差，让目标用户对号入座
命名：产品名 + 一句承诺（不是功能列表）
证据 1：一个真实动作链（找/装/验/更新）
证据 2：一个反直觉能力（零调用/上下文税/迁移）
证据 3：一个高频动作（召唤/套件/本项目）
落版：价值句 + 具体命令/入口
```

### 句式

- 一句只做一件事；8–24 个汉字。
- 动词优先：装、找、筛、验、禁用、释放、召唤、搬。
- 数字要有出处；没有就删。
- 少用“强大/一站式/全新体验/赋能”这类空词。
- 不要复用参考片的押韵、排比和 CTA 动词。
- 字幕关键词不等于旁白；旁白可以完整，字幕只留记忆点。

## 4. 钩子对照

| 弱钩子 | 强钩子 |
|---|---|
| “今天介绍一款插件管理工具” | “给 AI 装了这么多，你还记得几件？” |
| “支持四个市场” | “有些技能，装完就再没被叫过。” |
| “功能非常丰富” | “没被调用的工具，正在吃你的上下文。” |
| “快来试试吧” | “装得明白，也用得回来。” |

## 5. CTA

- 价值句 + 具体动作：`装得明白，也用得回来。` + `一行命令，搬进 DSH。`
- 或具体动作 + 条件：`dsh plugin --profile web add dsh-armory` + `装完完全退出再启动。`
- 不要复用参考片的 CTA 句式；不要用“快来”“立即体验”这种空 CTA。
- 命令上屏时用等宽字体，逐字打出或直接落版；旁边给重启/平台条件的小字。

## 6. 口播与字幕

- 口播：完整句、自然停顿、少用书面连接词。
- 字幕：关键词、可独立色块、位置固定。
- 同一句里不要既念长句又放长句字幕；字幕只留 2–6 个字的关键词。
- 中文引号用「」，命令用反引号/等宽；英文缩写按字母拆读。

## 7. 事实表模板

```md
## 事实表（版本 x.y.z）

| 上屏内容 | 出处 | 说明 |
|---|---|---|
| 版本 vX.Y.Z | package.json:3 | npm latest |
| 分类 A/B/C | lib/xxx.js:123 | 字面英文 |
| 按钮「安装」 | lib/xxx.js:456 | 忙碌态「安装中…」 |
| 命令 `...` | README.md:23 | 桌面端换 profile |
| 数字 19 万+ | lib/xxx.js:789 | 占位符原文，非实时 |

### 演示数据
- ...
```

写完后先自己逐条核对一次，再写旁白。画面上的每一个字都要能指回这张表。

## 8. 比喻合同（visual metaphor contract）

当视觉世界是产品里**不存在**的东西（星图、雷达、蓝图、卷宗），先签一份“比喻合同”，再写文案：

1. 第一次出现必须用“**比作 / 像 / 是看法**”，不能写成“把 X 连成 Y”“X 就亮了”。
2. 中段至少一句把话题交回**真实界面名词**（面板、市场、账本、菜单）。
3. 落版和封面各留一处**小字脚注**，写清实际入口。
4. 产品代码/README 里搜不到这个名词，就不要用“实现/生成/点亮/搬进”这类动词。

atlas 的写法：

| 位置 | 写法 |
|---|---|
| 产品第一次出场 | 如果把大肥鱼军械库**比作**星图，能力就有了坐标。 |
| 中段 | 星图是**看法**，**账本**记来路。 |
| 片尾 | 安装就这一句；重启 DSH，**面板里**就亮。 |
| 落版/封面脚注 | 星图为视觉比喻 · 实际界面在面板 / 市场 / 技能账本 |

反例：产品里没有星图，却说“把散落的能力连成一张星图”“重启后星图就亮”。观众会期待一个装完就出现的新界面，打开却是面板列表——这是预期落差，不是文案风格问题。

自检：**先在代码里搜隐喻名词。搜不到，它就是比喻，不是功能。**
